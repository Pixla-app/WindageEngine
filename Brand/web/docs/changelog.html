0.28.0 — 2026-10-13

SprintLatch is internal. It was public, but a game could neither make one nor read it; stick-click sprint latching reaches games through InputState, as it always did.

Removed

  • SprintLatch from the public API. Nothing changes for a game using InputState.

0.27.1 — 2026-10-13

The documentation, complete and in US English. Nothing compiled changes.

Documentation

  • Doc comments are US English, as the public names have been since 0.26.0 — swept now that the docs are published at windageengine.com, whose reference page quotes them. Code comments and these notes keep whichever spelling they were written in.
  • Four doc comments that had stopped being true are corrected: Frustum.planes said six planes (it is five), HUDRenderer said it draws no text (it does), the sample's debris said it casts no shadow (it has since 0.23.0), and AssetOrientation.read's parameter note used the old name.

0.27.0 — 2026-10-13

The British names are gone, one release earlier than 0.26.0 promised. The engine has no users outside the studio yet, and every game in it was moved to the new names in 0.26.0's pass — so the aliases protected no one.

Removed

  • Every deprecated alias from 0.26.0 — colour, centre, unitsPerMetre and the initializers and methods that took them. Use color, center, unitsPerMeter.
  • Reading a light's colour key in a level file. Every level in the studio was converted in 0.26.0; a level that still says colour now gets white light, the key's default.

0.26.0 — 2026-10-12

Public names are US English. The people writing games against this engine read and type these names, and nearly all of them write US English. Doc comments keep the old spelling for now; they are swept when the documentation is published.

Changed

  • colour → color: PunctualLight.color and init(position:color:range:cone:), ParticleRecipe.color and its initializer's color:, EngineMark.draw(…color:).
  • centre → center: BoundingBox.center, HUDRenderer.ring(center:…), CharacterController.Surroundings.Turn.center, Footprint.center and Footprint(center:…).
  • unitsPerMetre → unitsPerMeter: AssetOrientation.unitsPerMeter, its initializer and read(from:unitsPerMeter:).
  • Level files write a light's color, and still read colour, so every existing level opens. The sample's own levels are converted.

Changed — breaking

  • ParticleSystem.appearance(of:)'s tuple is labelled color. A tuple label cannot have two names, so this is the one rename with no alias.

Deprecated

  • Every old name above still works for this one release, forwarding with a fix-it (Deprecated.swift). They are removed in the next.

0.25.0 — 2026-10-12

Level of detail. A mesh gets simpler versions of itself when it loads, and a copy draws the coarsest one whose change in shape would cover under half a pixel where it stands. Measured where it came from — a world editor's wood of 1,000 trees of 19,000 triangles each on an M2 — 25 ms a frame after culling became 5.6 ms.

Added

  • MeshDetail — tiers(for:vertexDescriptor:normalAttribute:) makes up to ten tiers of a loaded mesh, each about half the triangles of the one before, each with its own vertices and normals recomputed from its own faces (kept normals drew far copies nearly black). choose(errors:distance:scale:pixelsPerRadian:) picks one. reductions(…) and tiers(_:full:…) are the steps, for a mesh that did not come from MeshLoader. CPU only; drawing a tier is the game's. Called tiers because Level is the level file.
  • A MeshOptimizer target: meshoptimizer 1.3's simplifier (MIT), vendored unmodified — the engine's first code not written in Swift. An app that ships MeshDetail ships Sources/MeshOptimizer/LICENSE.md.

Not in the sample

The sample's meshes are a few hundred triangles seen from a few metres, so no tier would ever be chosen and a demonstration would be staged. It is proved by a test that loads a real mesh through MeshLoader, and by the consumer it was extracted from. It goes into the sample the day the sample has something far away.

0.24.0 — 2026-10-12

A self-drawing shadow batch is told which pass it is drawing, so it can draw only what that pass can see. Measured where it came from — a world editor's scattered wood of 1,000 heavy trees on an M2 — drawing every copy into all four sun cascades was three quarters of the frame (75 ms with shadows, 19 without); culling each cascade to its own frustum brought the same frame to 25 ms.

Changed — breaking

  • ShadowMap.Batch(pipeline:encode:)'s closure takes a third argument, a ShadowMap.Pass: the cascade, atlas tile or cube face being recorded (index) and its light viewProjection — build a Frustum from it. A batch that draws everything ignores it ({ encoder, table, _ in … }). Released hours after 0.23.0, with no consumer outside this repository and the one it came from.

Added

  • ShadowMap.Pass — index and viewProjection, passed by ShadowMap, ShadowAtlas and ShadowCubes.

0.23.0 — 2026-10-12

Shadows for geometry the engine does not draw object by object. Instanced copies cast now, and so can a mesh a game builds into its own buffers — a heightfield it sculpts. And the cascades can be placed from any view, not only a `Camera`. Both came from a world editor putting the sun's shadows on a scattered wood, an orbiting view and sculpted ground; the sample proves the first with its debris.

Added

  • ShadowMap.Batch(pipeline:encode:) — a batch that encodes its own draws. The engine binds the pipeline and the light matrix, and hands over the encoder and argument table, once per cascade — and once per atlas tile and cube face, where ShadowAtlas and ShadowCubes draw it whole (it cannot be culled per object). Batch.encode is nil for an ordinary batch.
  • ShadowMap.BufferIndex.instances (4) — where an instanced shadow vertex function reads its copies' transforms. The three shadow passes' argument tables hold five buffers now.
  • ShadowMap.updateMatrices(frameSlot:cameraPosition:cameraForward:sunDirection:) — the cascades for a view that is not a Camera. The Camera form calls it, and a test holds the two to the same matrices.
  • The sample's debris casts shadows, sun and lamps, through sampleInstancedShadowVertex.

Changed

  • Recorded frames redrawn for the debris's shadows: long ones from the ruins' near brazier.

0.22.0 — 2026-10-12

Instancing. Many copies of the same meshes drawn once per submesh per kind, with an instance count, instead of once per copy. Extracted from working code in a world editor's scatter brush — a wood of hundreds of trees of two or three kinds — and proved here in the sample, which strews debris round each level's buildings as one batch.

Added

  • InstanceBatches<Key> — copies grouped by kind, kinds in the order first seen and copies in the order given, so a frame's draws come out in the same order every run. transforms is every copy's float4x4, kind after kind; each Batch has its first, count and byteOffset. No GPU: tested.
  • InstanceBuffer — one buffer per frame in flight, grown with room to spare and never shrunk, kept in the renderer's residency set as it grows. write(_:frameSlot:) returns the buffer to bind; the game's vertex function reads copies[instance_id] at the batch's offset. capacity(for:current:) is the growth rule, tested.
  • The sample draws debris instanced (SampleRubble, sampleInstancedVertex) — evenly sized, so the copy's transform turns normals with no inverse; scenery, so not in the shadow pass.

Changed

  • The sample's resources are processed, not copied as a folder. The SwiftPM that ships with Xcode 27 puts a copied folder one level deeper (Contents/Resources/Resources/), where lookups by name do not look — the sample started with no meshes, no sounds and no figure, and every recorded frame failed.
  • Recorded frames redrawn. The four scene frames now show the debris. The splash's is redrawn for 3 pixels of the host font's edge shading, which moved with macOS 27 — nothing of the engine's.

Not here — and why

  • LOD. There is nothing for it to choose between yet: no asset in the sample, and none in the scatter this came from, has lower-detail meshes. It arrives with the first that does, or with a scene that is too slow without it.

0.21.0 — 2026-09-15

The Drift W. 0.20.2 gave the engine a mark, and the mark was a diagram: a thin rule, a curve and two squares, 2.4 times as wide as it was high. It read as a chart going up, had no silhouette at a browser tab's size, and could not be an app icon. Six directions were drawn at every size that decides a mark — a 1024 icon, a Dock, a 16 px tab rendered into real pixels, a splash on dark and on white — and the one kept is a W drawn as one continuous stroke with its right half carried up 16% of its height. The initial, with the windage dialled in.

Changed — breaking

  • EngineMark is the Drift W. outline — thirteen points in a unit square, constructed from five points on the stroke's centre line and a stroke width — replaces pieces and Piece. aspect is 1, where it was 2.4: anything laid out against the old mark's width gets a square now. offset (0.16) is public, with the reason it is about as far as the lift can go.
  • SplashScreen sets one line across: the lead, the mark, WINDAGE over ENGINE — the shape a player has already seen on an engine splash. showsVersion defaults to false: no engine shows one in a shipped game. markWidthFraction sizes a square mark now, default 0.12.

Added

  • HUDRenderer.fill(polygon:color:feather:) — a filled polygon, concave or convex, either way round. The mark is a letter, and this renderer drew only rectangles, lines, rings and text.
  • HUDRenderer.triangulate(_:) — ear clipping, not a fan. Fanned from a corner, the W puts a triangle over the space between its own arms.
  • HUDRenderer.rim(of:width:) — an outline moved outward, mitred, the mitre held to three widths.
  • Brand/: the app icon on Apple's 1024 grid and a favicon beside the two one-tone marks, all written from EngineMark.outline and checked against it; Tools/make_brand_exports.sh rasterises them. And Brand/web/, a working draft of windageengine.com — see its README for the four things in it that are ahead of the facts.

Fixed

  • A filled shape's diagonals were stair-stepped. The HUD pipeline has no multisampling, so the W on its own splash came out jagged — at 640 × 400 and visibly at a window's size. fill feathers every edge over one unit, fading to nothing; the shader premultiplies, so the fade composites cleanly. feather: 0 for hard edges. The polygon's own triangles share their vertices exactly, so there is no seam inside it either — the hatching 0.20.2's quads needed a workaround for does not arise.

In the checks

  • The splash frame re-recorded, and each change shown to fail with it switched off: edges unfeathered, 0.12% of the frame differs and the splash's zero-pixel tolerance fails it; a fan instead of ear clipping, four tests fail (the fan spills outside the W, the triangles no longer add up to the outline, the rim reads as inside); the offset at 10%, all four Brand/ files disagree with the code and the splash frame fails by 0.16%.
  • 626 tests, 20 of 20 walk runs — the crate behind the splash included — 5 of 5 frames.

0.20.2 — 2026-09-12

The engine says its own name. Every engine somebody else ships with says so somewhere, and this one had no way to: no mark, no Brand/, nothing a game could show even if it wanted to. Nothing in LICENSE requires it — that file grants nothing to anybody yet — so this is a choice about what the engine is, and what the engine owes is the surface, not the decision.

Added

  • EngineMark — the device, as geometry: a straight rule where a shot was aimed, a square where it left, a path carried off the rule, and a square where it arrived. Windage is that carry. draw(into:x:y:height:colour:) puts it anywhere at any size out of the HUD's own primitives — no texture, no resource, no pipeline — so a game can credit the engine in a corner or an about box for nothing. Achromatic in two tones (display, deep): the mark appears inside somebody else's game, so a hue of its own would be a second brand competing with the one the player came for.
  • SplashScreen — the mark over a ground, with the name and version under it. Fades up, holds, fades away; skip(), advance(by:), isFinished, opacity, and a lead line ("MADE WITH"). Advance it from your step and draw it from your HUD: it is an overlay and a clock, never a mode, and skip() is a side effect of a press and never a consumer of one.
  • Brand/ — windage-engine.svg and windage-engine-display.svg, and the rules. Both are written from EngineMark.pieces and a test fails if the file on disk and the geometry disagree, so there is one drawing of the mark. Re-record with WINDAGE_RECORD_MARK=1 swift test --filter EngineMarkTests.

Fixed

  • A polyline drawn as a strip of quads has a seam at every joint, and it shows. Two quads meeting at a point end square to their own directions, leaving a wedge as wide as the turn — zero at the stroke's centre, (t/2)·tan(Δθ/2) at its edge. A comment here first called that "under a tenth of a pixel at any size", which was arithmetic done without looking: at a splash filling a 1440-point window it is two thirds of a point, and the curve came out visibly hatched. Found by running the sample and looking at it. Segments overlap by a twentieth of their length now, never past the two ends of the path.

In the sample

  • WINDAGE_SAMPLE_SPLASH=1|0 shows or hides it. Unset means on in ordinary play and off in a check or a recorded frame — a recorded frame is a picture of the scene, and a splash across four of them would be checking the splash four times and the scene never.
  • The sample does not pause for it, deliberately: the clock is already running when it fades. That is what makes the walk below worth anything.

In the checks

  • A fifth recorded frame, splash — taken at the middle of its hold, and without the version line, which changes every release: a frame carrying it would fail on the changelog rather than on the picture. It carries a tolerance of its own, and needs one: moving the mark's curve by 4% of its own height changes a quarter of a percent of a 640 × 400 frame, well inside the half-percent that is right for a lit scene. At pixels: 0, channel: 2 the same nudge fails it.
  • A 17th walk, "crate behind the splash" — the crate walk again, under the splash, checked against the crate walk's own recorded numbers (Tools/walks.json takes like, so there is one set of them). Make the splash swallow the press that skips it and the walk stands at the spawn and fails all three; the ordinary crate walk passes throughout.

0.20.1 — 2026-09-12

One course, four rates, one set of numbers. The rate independence was won a piece at a time — the flight (0.16.0), a landing's impact (0.17.0), the eye's settling (0.18.0), the slide (0.19.0) — and each piece has a test of its own, over one thing, from rest. This is the capstone: one course that walks, jumps, climbs three treads, sprints, slides, walks off a cliff and lands, with every error it collects carried into the next thing. No engine code changed; this is the proof that none needed to.

Added

  • A capstone test (OneCourseTests) over the whole body at 30, 60, 120 and 240 steps a second. Where it ends, what each of its three landings hit at, how high the jump inside it rose and how many times a foot came down are all computed, not read off a run — four wrong answers can agree with each other. Switched off one at a time: the old flight fails the jump and every landing at all four rates; the old landing speed fails every landing (0.41 m/s out at 30); the old slide fails the ending at all four (0.246 m short at 30, 0.033 at 240).
  • The floor on any of this is the Float, not the physics. A plain eight-second walk in a straight line — no jump, no slide, nothing but a step's travel added to a position — lands 0.1 mm from 48 m at 30 steps a second, 0.6 mm at 240 and 1.8 mm at 480. The course agrees to 1.5 mm, which is that.

In the sample

  • WINDAGE_SAMPLE_RATE=<steps per second> steps the simulation that often instead of the engine's 120, so the sample can be run at four rates and asked for one answer.
  • A scripted walk's segment boundaries are times from the script's start, not lengths of their own segments. A key can only be held for a whole number of steps, so a boundary lands on the nearest one; measuring each segment from the last boundary let those roundings add up over a script with forty segments in it. Every recorded walk is unchanged at 120 steps a second (15 walks, 79 expectations).
  • A 16th walk, course, run at all four rates (Tools/walks.py takes a rates list): up the ruins' stairs, off the landing, a jump, a sprint and a slide. Every line of its report is identical at 30, 60, 120 and 240 — the feet to the centimetre, the two landings at 6.9 and 6.3 m/s, the dips at 7 and 6 cm, the footsteps 2/4/0/0/0/2/0, and the slide ending 16.81 m along at x −19.81. Its segments are whole steps of the slowest rate (multiples of 1/30 s): nothing can make a 0.75 s press land anywhere but 0.733 or 0.767 at thirty steps a second, and 10 cm of walking is the cost.

Not covered, and said so

  • A law whose clock starts at a collision cannot be pinned by a course. The eye's settling is kicked when the feet climb something, and a climb happens on whichever step first overlaps the tread — a moment rounded by up to 33 ms at 30 a second, which is e^(−12·Δ), a third either way, on about a centimetre of lag. Switching the exponential back to 1 − rate·dt leaves the course's numbers alone. It is pinned where it can be — between two consecutive steps of one run — by 0.18.0's own tests.

0.20.0 — 2026-09-11

The frames are a check — and drawing one found a missing barrier. Every rendering capability here was judged by looking at a screenshot, and guarded by nothing: swift test draws no pixel and the walk check draws none either.

Fixed

  • The scene pass waits for the shadow pass, and the tone map for the scene. Metal 4 tracks no hazard between passes: the scene sampled shadow maps written by a pass in the very same command buffer, with nothing telling the GPU to wait. In play it looked right — the previous frame's maps are there to sample, so shadows were a frame stale — and the first frame of all came out differently on every run: a black scene, or one blotched in cluster-sized squares, from whatever was in that memory. Two consumer barriers (barrierAfterQueueStages:beforeStages:). Four runs of the same frame are now the same bytes.

Added

  • FrameRenderer.render(into:) — one frame into a texture of your own instead of a window's drawable, waiting for the GPU so it can be read at once. The same passes in the same order, so what comes out is what a player would have seen.

In the sample

  • WINDAGE_SAMPLE_FRAME=<path> draws one frame to a PNG and quits — no window, before any step, so the picture is the same every time.
  • Tools/frames.json, Tools/frames.py, Tools/frames/ — four recorded viewpoints (the ruins from above, the lintel at eye height, the courtyard, the turntable), drawn and compared pixel by pixel; a frame fails when more than 0.5% of its pixels differ by more than 5 in any channel. All four match to the bit; 15 s.

Measured

Proved by failing: the sample's tone map from ACES to Reinhard fails all four (98% of pixels, worst channel 48); nothing drawn into the sun's shadow maps fails all four (5.5–7.6% in the courtyard). Two first attempts proved nothing and were caught: changing ToneMapping's default curve, which the sample overrides; and multiplying the constant depth bias by 25, which is too small to see against a cascade's depth range.

A slide covers the ground its curve says, at any step rate. Its speed falls from a sprint's to a crouch's along r^0.35; the step took one reading of that curve and held it, so a slide came up shorter the more coarsely a game stepped.

0.18.0 — 2026-09-11

The eye settles as the exponential it is. A rate per second was taken as 1 − rate·dt a step — the first two terms of e^(−rate·dt), short by the rest, and zero at dt = 1/rate: a game stepping twelve times a second closed the whole gap in one step and snapped where a faster one eased.

Changed

  • settling, bobCatchUp and the head bob's easing take e^(−rate·dt) — the curve their rates describe. The eye lags a little longer after a step up, by the terms the old form dropped: 5% of a step's share at 120 a second.

Measured

Up four treads the eye ended 1.640 m above the feet at 30 steps a second and 1.636 at 120; it is the same at every rate now. Two tests: a step leaves exactly e^(−rate·dt) of the lag at 10, 30 and 120 steps a second — and there is a lag to leave, where at 10 the old form left none at all — and a second of settling is the same in one step or a hundred. All three rates fail on the old form; the 10 passed it only because both its readings were zero, which is the snap.

Nothing the walks record moved: 15 walks, 79 expectations, including the head bob to the millimetre.

A jump rises the same however often a game steps. The fixed timestep keeps results independent of the frame rate; the step rate is a game's own choice, and the jump was integrated a step at a time by the velocity each step ended at, which loses ½g·dt² every step.

Extracted, and three things changed on the way

The simulation came from a working game: fixed step, deterministic, fixed pool, and the oldest particle recycled when full, never the newest — the newest burst is the one the player is looking at.

  • Kinds became recipes. The game had an enum of its own kinds. An engine cannot; the next game's kinds are different ones. What was shared was the shape of a kind, which is ParticleRecipe.

A spark makes light; dust covers what is behind it. Premultiplied alpha serves both: matter writes its opacity as coverage, light writes zero, and the same blend becomes an add. One pipeline, one draw, no sort between two kinds.

0.6.5 — 2026-09-10

Things that hang off other things. TransformHierarchy is parenting — one transform expressed relative to another, resolved in the right order — and the sample's figures now carry lanterns.

Added

  • TransformHierarchy — attachments, local transforms, and one forward pass to world transforms. Parent-first is checked at construction, as in Skeleton.
  • matrix_without_scale(_:).

It is parenting, and deliberately not a scene graph

A scene graph is an object model: nodes that own children and components, are looked up by name, and become the unit everything else is written against. That decision is in the README's contested list and stays there. What a game runs into first is much smaller, and this is that: a list of attachments and a list of matrices, owning no objects at all, so the same hierarchy can drive a drawable, a light and a collision volume without knowing any of them exist.

The interesting case is the one that reaches outside

A rig is already a hierarchy and SkeletonPose already resolves it. What it cannot do is reach out — and the canonical attachment, a weapon in a hand, is exactly that: the parent is a joint, inside a pose, that is itself placed by an object's world transform.

Attachment.external(_:) makes that first-class. The node's own local transform stays what it should be — the grip, authored once — instead of being rewritten every frame by a caller who then has to keep the grip somewhere else anyway. How many external transforms will arrive is declared up front, so an out-of-range attachment is a load-time error rather than an identity substituted at sixty hertz.

Scale is inherited, and that is wrong for a held object

A rig authored in centimetres hands its wrist a hundredfold scale. It belongs to the arm — the forearm genuinely is fifty units long in that space — and it is exactly wrong for something merely hung there: the lantern comes out at one percent of its size, in a position that is otherwise correct, which reads as the wrong mesh rather than as the wrong space.

matrix_without_scale at the call site, rather than a "do not inherit scale" flag inside the hierarchy, because it is a decision about what is being attached and only the caller can see that.

A joint's frame is not a promise about where the mesh got drawn

The bind pose puts the sample figure's forearm joint 48 cm along the arm and the mesh reaches 74, so 26 cm along the joint's +X reads as "the hand" — and with the arm down it is exactly that. Raised, it is not: the drawn limb stops a hand's length short of where that arithmetic says the hand went.

That gap is the asset's business rather than the engine's, and the useful form of it is a warning: a grip derived from bind-pose arithmetic is a guess. It is a number set by looking, which is what an attachment point in a tool is for.

0.6.4 — 2026-09-10

Point lights cast now. Every lamp in the sample stops at a wall, aimed or not, which finishes what 0.6.3 started and left costed.

Added

  • ShadowCubes — a cube-array depth texture, the six face matrices, and the pass that records them. Six render passes per light, with two culls that take most of that back.
  • ShadowMap.Batch.bounds — an optional world-space box per drawable. Additive and defaulted to nil, so existing batches compile and behave exactly as before.
  • BoundingBox.expanded(by:).

A cube array, not tiles of the atlas — which is not what 0.6.3 said it would be

The atlas's own note said the missing feature was "cube tiles in the atlas, six passes per light, and a shader that picks a face before it picks a tile". Two thirds of that survived the work. The tiles did not, for two reasons that only appear once the shader is written.

The face maths has to agree with six matrices, exactly. Picking a face by hand means reproducing the cube convention — which axis becomes u, which becomes v, which of the six sign flips applies — in a shader, and matching it against six matrices built on the CPU. Every one of those is a place for a face to come out rotated or mirrored, and what that produces is a plausible shadow in the wrong direction.

And a filter kernel cannot cross a tile edge. A tap that steps off the edge of a face does not land on the next texel of that face; it lands on a different face at a right angle. Clamping draws a bright seam down all twelve edges of the cube, and not clamping reads a neighbouring lamp's tile.

A typeCubeArray texture hands both to the hardware: the sampler takes a direction, picks the face itself, filters across the seams itself, and compares itself. What is left on this side is the six view matrices — and those are pinned against the same convention in the tests.

The bias is in metres, not in depth

A cube face stores near / distance, so a constant added to that depth is a third of a millimetre at one metre and most of a metre at ten. A bias tuned to remove acne beside the lamp deletes contact shadows across the room. Taken off the distance instead — scaled by the face's own texel size — it is one number at every range.

Six passes, and what the culls give back

A caster outside the light's range is skipped for all six faces; one outside a face's Frustum is skipped for that face. In the sample's ruins, two casting point lights across 32 drawables: 35 objects recorded against 384 unculled. Thirty-two drawables is what one unculled pass costs, so all twelve passes together came to barely more than one of them.

Frustum has been in the package since 0.4 and had no consumer inside this repository until now.

Two smaller ones

  • right × up == forward for a cube face, which looks like the wrong handedness and is not. A cube is sampled from the inside, so its faces are mirrored relative to a camera looking out. The same relation already held for the spot's view and for the cascades, so the winding — and the front-face cull — is unchanged in all three.
  • The near plane travels with the light rather than sitting in a shader constant, because it is what the shader's reference depth is made of.

Verified twice

The six matrices are checked against the sampler's own rule on the CPU: for a spread of directions, the face the rule picks and the uv it gives have to be where that face's matrix actually lands the point. That is the half a screenshot cannot show — a mirrored face still casts a shadow.

The other half was a difference: the same frame with the per-light cube flag on and off changed 1.77% of it, all of it around the two braziers.

0.6.3 — 2026-09-10

Shadows for the lamps. A spot light casts now, so a wall stops it — which it had not, and which was the reason the sample's ranges were kept short.

Added

  • ShadowAtlas — one depth texture cut into tiles, a spot's view-projection, and the pass that records every caster into its own tile.

An atlas rather than a texture each

A texture per light is an allocation and a residency entry appearing and disappearing as levels load, a render pass each, and a shader indexing an array of textures. One texture cut into tiles is a fixed allocation, one render pass for every light — the viewport moves between them — and a single binding sampled with an offset.

Scissored as well as viewported, which is not redundant: a viewport limits where geometry lands and does not stop a clear or a wide triangle touching a neighbour's tile. One lamp bleeding into another's map is a shadow that appears in the wrong room.

Spot lights only, and the cost of the rest is written down

A spot's shadow map is one perspective render, the same shape as a cascade and sharing its pipeline. A point light needs six — a cube, one face per direction — so shadowing every lamp costs six times what shadowing the aimed ones does. viewProjection(for:) returns nil for a light with no cone rather than silently shadowing one direction of six.

Four smaller ones

  • The field of view is the cone's outer angle doubled (and a little more), so the map covers what the light reaches — no less, which cuts the shadow off inside the lit circle, and no more, which spends resolution on nothing.
  • A lamp pointing straight down is the common case and exactly where a fixed up vector is degenerate. The cross product is zero, the basis becomes NaN, and nothing draws.
  • The shader's constant bias is positive where the rasteriser's is negative. They are different quantities in different spaces — one is normalised light depth, the other a rasteriser offset — and reversed-Z inverts the sign of only one of them.
  • Tiles go to the brightest, longest-reaching lamps. A light nobody can see casting a shadow nobody can see is the tile to give away first.

Verified by difference, not by looking

A spot shadow on open ground is subtle enough that "looks about right" is not verification. The same frame was rendered with the per-light shadow flag on and off: 1.2% of the frame changed, confined to the lit ground. That is what said the atlas was working before any effort went into finding a camera angle that showed it off.

0.6.2 — 2026-09-10

Clustered shading. A fragment asks which lights reach it, instead of inheriting a list chosen for the whole mesh it belongs to.

A large addition on a patch number, which is the versioning rule working as intended: the number tracks compatibility, not significance. Nothing that compiled against 0.6.1 changes.

The problem it fixes, which 0.6.1 found and could not solve

LightSet picks a few lights per object — correct, cheap, and only as good as the draws are small. The sample's ground is one eight-hundred-metre quad, so a single draw got four lights for an entire level and a spot five metres up lost to lamps standing closer to the plane. No budget and no ordering rule fixes that; the object is simply the wrong unit to choose lights for.

A cluster is the right unit: a small box of the world, so the lights reaching it are few by construction, and a fragment belongs to exactly one.

Added

  • ClusterGrid — the frustum cut into tiles and depth slices, with the slicing a shader needs as two constants and a logarithm.
  • ClusteredLights — bins lights into the clusters they reach, as the two arrays a shader reads.

Three decisions worth the words

  • Slices are exponential. Cut the depth evenly and the near slices are microscopic while the far ones are hundreds of metres deep — a perspective frustum's cross-section grows with distance, so an even cut puts almost every cluster where there is almost no screen. Slicing by the logarithm makes each cluster roughly cubic.
  • Clustering needs a finite far and this engine's projection has none. The infinite far plane is deliberate — no view distance to tune, nothing to clip at range — so ClusterGrid carries its own lightRange. Honest rather than awkward: a punctual light has a finite range by definition, so there is a distance past which none of them reaches.
  • An offset and a count per cluster, not a fixed list. A fixed list means every cluster pays for the worst one — three thousand cells times a budget of eight is twenty-four thousand entries, nearly all empty. A range into a shared list costs an empty cluster nothing and puts no ceiling on a full one.

Measured

Sixty-four lights in a test scene: busiest cluster 9, average 2.2. The sample's ruins: ten lights, busiest 6. That ratio is the whole point — the worst fragment loops nine times instead of sixty-four, and the typical one twice.

The bug that made it render as nothing at all

The first working version drew no local light whatsoever, with the CPU side provably correct: six lights, 222 cluster entries, 173 cells occupied.

A SIMD3<Float> used as padding has 16-byte alignment in Swift; the shader's three trailing scalars have four. The struct came out 48 bytes on one side and 32 on the other, so every field after it in the frame uniforms was read from the wrong address. It compiled, it ran, and it looked exactly like a feature that had not been wired up.

There is a test pinning the layout now — size, stride and alignment — because a struct that agrees on its fields and disagrees on its padding is the worst kind of mismatch.

0.6.1 — 2026-09-10

Spot lights — a cone, for the lamps that are aimed.

Added

  • PunctualLight.Cone — a direction and two angles: full brightness within the inner, nothing beyond the outer, smooth between. Two angles rather than one, because a single cutoff gives a hard-edged circle that reads as a stencil rather than as a lamp.
  • PunctualLight.angularAttenuation(at:) and .radialAttenuation(at:), the second being distance alone.
  • Levels write a cone by naming a direction and angles in degrees, like the sky's. No direction means no cone, so every lamp already written stays a point light.

A point light is a spot with no cone, and the shader does not branch

Its angleScale is 0 and its angleOffset is 1, which makes the angular term evaluate to exactly 1 everywhere — from the same two multiplies. One code path, no branch, and nothing that behaves differently depending on which kind of lamp a level happens to hold.

A cone cannot be tested at one point, and the error has a direction

The nearest point of a box gives the best distance, and for a point light that settles which lights reach it. For a spot it does not: the nearest corner of a wall can be outside the cone while the far end of the same wall is brightly lit. Testing that one point drops the light and the lit end goes dark.

A false positive costs one iteration of a shader loop; a false negative deletes light the player can see. Those are not comparable — the same asymmetry Frustum is built around — so the cone is tested against the box's bounding sphere, which can say yes when the answer was no and never the reverse. Ranking is by distance alone for the same reason.

And a finding that was not about spot lights at all

The sample's new spot lit nothing, and over-subscription was not why — isOverSubscribed reported the level clean at every point a player stands. The cause is that the ground is one 800-metre quad. Per-draw selection gives it four lights for the entire level, so the objective lamps standing 0.6 m above it beat a spot 5 m up, and the spot never reaches the shader.

Per-draw light selection is only as good as the draws are small, and no budget or ordering rule fixes an oversized one — that is what clustered and tiled shading exist for. The sample aims its spot at a pillar instead, which is a normal-sized draw, and the limitation is written down rather than tuned around.

Also

The sample reports over-subscription at load, sweeping the points a player actually goes. A condition nobody checks is a condition nobody meets.

0.6.0 — 2026-09-10

Lights that are not the sun. A directional sun and an environment map light an outdoor scene correctly and have no answer at all for an interior — the sun does not reach inside, and a sky-coloured ambient lights a cellar as though the sky were overhead.

Extracted from a probe built to ask exactly this, and stripped of the game that asked it.

Added

  • PunctualLight — a position, a radiant intensity, a range, and a physical windowed inverse-square falloff.
  • LightSet — a budget and the rule for choosing which lights fill it, plus isOverSubscribed(at:).
  • Level.lights, a named list in the level format.
  • BoundingBox.closestPoint(to:).

Changed

  • Level decodes explicitly and tolerantly now. Every field but the version is optional, because the synthesised decoder throws on a missing key — so adding lights would have refused every level already written, including any a player edited into Application Support.

What the probe had wrong

It ranked lights by falloff alone, ignoring how bright they are — so a candle at one metre outranked a floodlight at ten, and the floodlight was the one dropped. Influence is weighted by luminance now, which costs a dot product and makes the ordering mean what it claims.

What the probe had right, and it is the important part

A hard budget cannot promise a smooth hand-over in an arbitrary level. If five lights all contribute at a point, one is dropped, and how visible that is depends entirely on how the level was built. Ordering by influence does not save it and a bigger budget only moves the number.

So the promise is conditional: where no more than the budget are above negligible, nothing the player can see is ever dropped — and isOverSubscribed(at:) is what makes that checkable before a corridor ships with a flicker in it.

Four smaller ones

  • Selection is per draw and uses the box's nearest point, not its centre. A long wall whose middle is out of a lamp's reach still has an end inside it.
  • The falloff needs a floor. A fragment exactly at a lamp's position is a division by zero, and the pixel that produces is not "very bright" — it is NaN, which draws black.
  • Local lights cast no shadows. There is one shadow map and the sun has it, so a lamp reaches through a wall. That is why the sample's ranges are short: it is only obvious when a lamp reaches far enough for it to be.
  • A lamp in daylight does almost nothing, which is correct and is why the sunlit level has none. Its local lighting is the objectives, which are dynamic — so between the two levels both paths are exercised: lamps from the file, and lights the game owns.

Radiance is not irradiance, and they differ by about 130×

The one that would have been a silent disaster. sunRadiance is how bright the disc is, looked at. What a surface receives is that times the solid angle the disc subtends — and a 0.05 radian disc subtends 0.0079 steradians. Use the radiance as a directional light's intensity and the scene is a hundred and thirty times too bright.

Deriving one from the other is what stops the sun you see and the sun that lights the scene being two numbers that can disagree, and it makes a physically true thing fall out for nothing: a wider sun is both softer and stronger, because it is more sky.

0.4.1 — 2026-09-10

Image-based lighting. A surface takes light from its whole environment, and how it takes it depends on how rough it is — a mirror reflects one direction, chalk gathers the hemisphere. Both are precomputed now, so a metal object reflects its surroundings instead of a gradient.

Added

  • ProceduralSky — a sky as a function of direction: gradient, horizon, ground bounce and a sun disc, in radiance rather than colour.
  • EnvironmentMap — that environment convolved twice: specular, a cube whose mips are the GGX lobe at increasing roughness, and irradiance, a small cube convolved with a cosine lobe.
  • The sample draws its sky from the same cube it reflects, and shades with both.

Built on the CPU, deliberately

Every part of this that can be wrong is arithmetic — cube face projection, importance sampling, two convolutions — and this repository's rule is that such halves want tests and tests should not want a GPU. A compute prefilter would be faster and would put all of it somewhere only a screenshot could check.

Cost: 92 ms in a release build, 2.6 s in a debug one. The debug figure is what somebody running swift run WindageSample sees, and it is the honest price of doing this in Swift on the CPU. It prefilters a function, not a photograph; an engine wanting to prefilter a captured HDR panorama will want the compute version, and this maths is what that would be written against.

Three things the tests found

  • Fireflies at high roughness. At a fixed 96 samples the chain stops getting blurrier around roughness 0.6 and starts getting brighter — 0.72 rising to 1.67 at roughness 1.0, where the truth falls to 0.60. A wide lobe over a small, very bright sun means the estimate is decided by whether a sample happened to land on the sun. Fixed by quadrupling the sample count per mip, which is free: each level has a quarter of the texels, so the cost per level is flat and the roughest mips — which need it most — are the cheapest place to spend it.
  • The irradiance integral was out by a factor of π. It is a Riemann sum over dφ dθ, so each term is worth step² of measure; dividing by the sample count gives an average instead. Caught by asserting that a uniform sky of radiance L integrates to πL.
  • The lower hemisphere must not be black. A surface facing down is lit by the ground, and a black ground is the commonest reason an image-based lit object looks like it is floating in a void.

And one in the shader

Irradiance is not radiance. The cube holds light integrated over the hemisphere; Lambert's BRDF is albedo / π, and skipping the division makes every ambient-lit surface π times too bright.

Where the BRDF lives, and why it is not here

In the sample. The engine owns when things happen, the depth convention and the tone map; what a surface is — its BRDF, its lighting model, how many lights it takes — is a game's, and no two games will agree. If a second consumer writes this same function, that is the moment to extract it — which is the lesson the shadow pass taught, applied forward rather than after the fact.

Five things worth knowing

  • Metal with no environment is black. A metal surface has no diffuse at all; its entire appearance is what it reflects. With only a sun in the scene it is black except for one small highlight, so something has to stand in for an environment — here, a two-colour sky gradient and a mix.
  • alpha is roughness squared, and the squaring is not decorative. Roughness is authored perceptually so a slider steps evenly; the distribution wants the physical quantity, and feeding it the perceptual value bunches all the useful range into the first third.
  • Fold 1 / (4 NdotL NdotV) into the visibility term. Written separately, both it and the geometry term vanish at grazing angles and the division is a ratio of two vanishing numbers — a bright rim of fireflies along every silhouette. Combined, the zeros cancel algebraically.
  • Roughness has to be clamped away from zero. A perfectly smooth surface is a delta function: infinitely small, infinitely bright, and on screen a single crawling pixel.
  • kD = 1 − F. What is not reflected is what is available to scatter. Skipping it makes a shiny surface brighter than the light falling on it, which is the usual way a first PBR shader breaks energy conservation.

Still missing

A real prefiltered environment map. The analytic sky is enough for metal to read as metal and is not enough for a metal object to reflect its surroundings.

0.1.1 — 2026-09-09

Everything a real character needs that a generated one did not show. An 87-joint rigged character from an actual toolchain was loaded, and it arrives in three shapes the engine had no answer for. Additive: nothing that compiled against 0.1.0 changes.

Added

  • AssetOrientation — the up axis and unit scale an asset was authored in, and the one matrix that corrects it. A character out of a game-engine toolchain by way of Blender arrives Z-up and in centimetres; applied in front of the model matrix, one matrix corrects the mesh, the rig and the animation together, because skinning happens in model space.
  • RigLoader.clips(named:withExtension:bundle:) — reads only the animations from a file.
  • RigLoader.load(named:withExtension:clipFiles:bundle:reportingTo:) — a rig from one file and its animations from others, which is how a character exported one clip at a time arrives. A file holding one clip has it renamed to the file's own name. A clip that drives none of the rig's joints is dropped and reported; a clip file that is missing is reported, not thrown.
  • Rig.adding(_:) and Rig.jointsNotDrivenBy(_:).
  • AnimationClip.renamed(to:) — for the names an exporter produces.

Changed

  • The sample's figure is now written the way a real export arrives: Z-up, a hundred units to the metre, and its second clip in a file of its own whose copy of the skeleton has the wrong rest pose. It renders identically to the Y-up metre version it replaced, which is the point. A sample that only ever loads tidy assets leaves the untidy path untested.

Notes for anyone loading a real character

  • A clip file's skeleton is not the rig's skeleton. Its rest pose is wherever the exporter left the rig — usually the clip's first frame. Measured: one joint reports (10.42, 4.08, 7.84) in the base file and (3.16, 1.17, 7.84) in the walk file. Merge them and every joint a clip does not animate stands in the wrong place, and the fault changes with which files were loaded.
  • Model I/O exposes upAxis and not metersPerUnit. The axis can be read; the scale has to be measured once and written down.
  • Each per-clip export carries a whole copy of the mesh. Model I/O offers no way to open an asset's animations alone, so the parse cost stays; what clips(...) avoids is the expensive half, since nothing is laid out or uploaded to a GPU without a vertex descriptor and an allocator.

0.1.0 — 2026-09-09

The first version with a number. Everything before this was a folder inside a studio repository, consumed by one game that was developed alongside it — so there was nothing for a version to mean. It is 0.1.0 rather than 1.0.0 deliberately: the API is not settled, and saying so in the number is cheaper than discovering it in somebody else's build.

Added

  • Frame pacing and frames in flight. FrameRenderer drives the loop from a CAMetalDisplayLink, owns the depth buffer and the reversed-Z clear value, and hands a game four methods to implement (GameLoop). FixedTimestep separates simulation rate from frame rate and reports the interpolation fraction for rendering between steps.
  • The reversed-Z convention, enforced rather than documented. matrix_perspective_right_hand_reverse_z, FrameRenderer.makeDepthStencilState() and FrameRenderer.reversedZClearDepth are one set: use all three and the projection, the compare function and the clear value cannot disagree. A depth-slice variant projects a first-person viewmodel into the front of the buffer.
  • Camera — position, yaw and pitch, mouse and stick look, and interpolation between two cameras for rendering between simulation steps.
  • InputState — keyboard, mouse and gamepad behind one interface, with StickResponse for dead zone and response curve, and SprintLatch for holds that have to survive a frame boundary.
  • MeshLoader — geometry through Model I/O, laid out to match a pipeline's vertex descriptor, with per-submesh materials and the mesh's bounds.
  • Skinned animation — Skeleton, AnimationClip, JointTransform, JointTrack, AnimationBinding, AnimationPlayhead, SkeletonPose and RigLoader. Rigs and clips load from USD, clips cross-fade, and the result is a joint palette a vertex shader indexes.
  • Materials and textures — Material (the metallic-roughness set), TextureSlot (which decides sRGB decoding, because that is a property of the map and not of the call site) and TextureStore (loads once, caches, mipmaps, and carries 1×1 fallbacks).
  • ShadowCascades — cascade splits, the light basis, texel snapping, per-cascade depth bias derived from the world size of a texel, and the blend bands between cascades.
  • Frustum — the planes of a view-projection and a conservative box test. Five planes, not six: the engine's projection has an infinite far plane.
  • BoundingBox and Volume — an extent, where it is, and one segment hit test shared by everything that asks "what is out there".
  • Level and LevelEditor — a versioned level format with placements, markers, tags and anchors that resolve against ground the game supplies; and the operations an in-game editor needs, with undo.
  • HUDRenderer and FontAtlas — text and quads drawn after tone mapping, in the same pass, with an atlas that can be asked for characters beyond ASCII and says what a font could not supply.
  • AudioEngine — positional playback with a listener that follows the camera.
  • SaveStore — injected rather than global, so tests do not fight over one file.
  • ShaderLibrary — finds a compiled Metal library, and compiles from source when there is none, because swift build compiles no Metal at all.
  • WindageSample — a complete small game built against the public API only: two levels loaded from JSON, an in-game editor, cascaded shadows, positional audio, animated characters, textured surfaces, a win/lose loop and a save. It is the standing check that somebody who did not write the engine can build with it.

Known gaps

Not a list of bugs — a list of things a consumer will look for and not find. The reasoning, and which of them are waiting on evidence rather than on time, is in README.md § "Where this engine actually stands".

  • No normal mapping in any consumer: the slot and the sRGB rule exist, tangents in the vertex layout do not.
  • No animation state machine, retargeting, IK or root motion.
  • No transform hierarchy between objects — a rig is one, objects are a flat list.
  • No post-processing or tone-map curve; each game supplies its own.
  • No particles, character controller, LOD or instancing.
  • The shadow pass is not extracted — only the arithmetic behind it.
  • macOS and Metal 4 only.
